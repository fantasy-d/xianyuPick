## 当前结构边界
- `source_channels`
  - 负责“渠道账号池”的真源配置与运行时登录态管理。
- `crawl_config`
  - 负责“抓取策略”的配置。
- `决策资产库`
  - 负责回显“实际抓取结果”
  - 因此不能只依赖当前系统配置推断渠道，必须尽量保存抓取当时使用的渠道元数据
- 因此“货源渠道配置”更适合加在 `crawl_config` 下，而不是塞回 `source_channels`。

## 本次计划的核心问题
1. 抓取配置是选择“渠道”，还是选择“渠道 + 账号”。
2. 抓取配置是否允许选择未登录成功的账号。
3. 当账号池发生变化时，抓取配置如何自动收敛。
4. 抓取运行时是只读“当前激活账号”，还是允许额外定制抓取范围。
5. 决策资产库如何展示“该资产使用了哪些渠道”。
6. 详情页是前端临时分组，还是后端直接返回渠道分组结构。

## 当前建议
- 抓取配置只允许选择：
  - 已存在于“货源渠道号池”中的渠道
  - 且该渠道下“登录成功并已加入当前激活账号”的账号
- 保存时仅保留：
  - `channel_id`
  - `account_ids`
  - `enabled`
- 不保存：
  - `session_report`
  - `state_file`
  - `user_data_dir`
  - `profile_directory`
  - `cookies_source`
- 抓取结果落库时应额外保存：
  - `source_channel_id`
  - `source_channel_label`
  - `source_account_id`
  - `source_account_label`
- 决策资产库应展示：
  - 列表页：本资产涉及的渠道标签
  - 详情页：按渠道分组后的货源列表

### 保存时的联动收敛更适合“显式告知”而不是静默处理
- 当前保存抓取配置时，后端已经能根据 `source_channels` 自动过滤：
  - 不存在的渠道

- 因此当前决策调整为：
  - 保存成功仍返回 `success`
  - 但在 `msg` 中追加“自动移除 / 自动收敛”的明细
- 这能更好地覆盖计划中“联动规则与边界处理”的用户感知层要求。

## 备选设计

### 方案 A：仅选择渠道，账号完全跟随“当前激活账号”
- 优点：
  - 简单
  - 联动成本低
- 缺点：
  - 用户无法在抓取配置里区分“这个渠道下哪些账号参与抓取”

### 方案 B：选择渠道 + 账号
- 优点：
  - 表达力更强
  - 真正实现“抓取策略层”的配置能力
- 缺点：
  - 需要处理双层配置同步与失效收敛

### 当前倾向
- 倾向方案 B。
- 但运行时首期可先保守实现为：
  - UI 与配置层允许“渠道 + 账号”
  - 抓取入口先按配置筛出账号集合
  - 具体是否轮询这些账号，视现有抓取链路改造成本再定
- 对资产展示层，倾向于：
  - 后端至少返回每条 `source` 的渠道字段
  - 前端可先自行分组
  - 若后续复杂度上升，再升级为后端直接返回 `channel_groups`

## 与既有计划的边界

  - 不应只改系统设置页而遗漏资产展示
